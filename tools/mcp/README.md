# tools/mcp — MCP servers and skills for Claude (MoW:AS2, AS64, Gates of Hell, the ARSENAL GUI)

Contract for everyone who builds a part. Frozen names; add, do not rename.

## What ships
- `tools/mcp/server.js` stdio MCP server `arsenal` (JSON-RPC 2.0, newline-delimited, no deps, node only). Loads every `tools/mcp/tools/*.js` module. One server for all three games: every tool takes `game` = `as64 | mowas2 | goh` (default from env `ARSENAL_GAME`, else `as64`). The games share most engine and data rules, so ONE tool serves all three and names the differences in its answer; a tool that a game can not serve says so in plain words (`{ na: 'why' }`), it does not vanish.
- `tools/mcp/gui.js` stdio MCP server `arsenal-gui`: talks to a running GUI (`node tools/gui/gui.js`) over HTTP on localhost. The GUI picks a free port unless `--port` is given; the server finds it from `%LOCALAPPDATA%\ARSENAL\gui.json` (env `ARSENAL_GUI_PORT` overrides) and never prints the session token kept there. Its tool list is generated from the GUI's own route and page registry, never typed by hand.
- `.mcp.json` at the repo root registers both for Claude Code. `tools/mcp/install.md` says how to add them to Claude Desktop and to a plain `claude mcp add`.
- `tools/mcp/CATALOG.md` generated by `node tools/mcp/catalog.js`: every tool of both servers and every skill, one line each. `tools/mcp/test/run.sh` fails when it is stale.

## Tool module contract (`tools/mcp/tools/<group>.js`)
```js
module.exports = { group: 'mod', tools: [ {
  name: 'mow_mod_check',                 // mow_<area>_<verb>, lower case, frozen once shipped
  title: 'Check a mod',                  // short, plain words
  description: '...',                    // when to use, what comes back, per-game notes
  inputSchema: { type: 'object', properties: {...}, required: [...] },
  games: ['as64', 'mowas2', 'goh'],      // games it serves
  kind: 'read' | 'write' | 'launch',     // write = changes files, launch = starts or drives the game
  handler: async (args, ctx) => ({ text: '...', data: {...}?, isError: false })
} ] };
```
`ctx` (from `tools/mcp/lib/ctx.js`): `game(args)` -> `{ id, exe, dir, profile }` (install folder from env `ARSENAL_AS2_DIR`, `ARSENAL_GOH_DIR`, else the GUI settings file, else Steam library scan; `mowas2` and `as64` share one install), `run(tool, argv, opt)` (spawns `node tools/<tool>/<tool>.js` with an argv array, no shell, timeout, output cut to 40k chars), `q(args)`, `guard.write(path)`, `guard.launch()`, `bad(msg)`.

## Safety rules every tool keeps
- Game installs, vanilla data and existing mods the user did not name are read-only.
- `kind: 'write'`: answers a preview unless `write: true` is passed; the target must be inside a folder listed in env `ARSENAL_WRITE_ROOTS` (`;` separated) and never inside a game's own `resource` or `packages`; refusal in plain words. No tool deletes.
- `kind: 'launch'`: refused unless env `ARSENAL_ALLOW_LAUNCH=1`. Starting the game, driving its menus, switching the enabled mod list are launch tools. A launch tool whose schema declares `dry` runs with `dry: true` without the switch: it answers what it would start and starts nothing.
- Arguments go to child tools as an argv array; a value starting with `-` is refused where a path or name is expected.
- No network calls, no credentials, nothing about the user in any output.

## Tools of `arsenal-gui`
`gui_status`, `gui_pages` (tabs and pages with what each is for), `gui_routes` (API routes with fields, generated), `gui_call` (one route; write routes need `write: true` in the body the same way the page does), `gui_jobs`, `gui_open` (page link for the user), `gui_lang` (a page string by key). `gui_start` (start the window; launch kind, needs `ARSENAL_ALLOW_LAUNCH=1`).
Write safety of `gui_call`: every route carries a write class in `gui/registry.json` (`no`, `flag`, `dry`, `always`, `unknown`, `blocked`, `launch`, `command`). `flag` routes preview unless `body.write` is true; `dry` routes get their dry flag set unless `body.write` is true; `always` and `unknown` routes are sent only with the tool argument `confirm_write: true`; a real write must name folders inside `ARSENAL_WRITE_ROOTS`; `blocked` routes (remote access, keys) are never sent. Port: the `port` argument, `ARSENAL_GUI_PORT`, `gui.json`, then 47811.

## Skills (frozen names)
Modding: `mow-mod-start`, `mow-mod-units`, `mow-mod-weapons-damage`, `mow-mod-maps-missions`, `mow-mod-text-ui`, `mow-mod-ai-bots`, `mow-mod-check-fix`, `mow-mod-together`, `mow-mod-port` (GoH <-> AS2), `mow-mod-test` (run it in game, read the log), `mow-mod-share`.

GUI: `arsenal-gui-use` (do a task through the GUI or its MCP), `arsenal-gui-dev` (rules for changing the GUI).

## Keeping it current
- GUI route or page added, renamed or removed -> `node tools/mcp/catalog.js` (regenerates CATALOG.md and the GUI tool list), update `arsenal-gui-use` if a task path changed. `tools/mcp/test/run.sh` and the GUI test `test-mcp.js` fail on drift.
- New CLI tool worth exposing -> add it to a tools module, a line in the skill that covers the task, `catalog.js`.
- New game fact -> the knowledge webs first; skills point at the webs, they do not copy facts that change.

## Pieces, groups and downloads (second batch; frozen names)
Goal: Claude loads little. Every skill is a short router (SKILL.md under 60 lines) plus sub-files of under 80 lines each, one per sub-task, read only when that sub-task comes up. Every MCP tool sits in a small group, and a server can be started with only the groups wanted.

- `node tools/mcp/server.js --groups a,b` (or env `ARSENAL_MCP_GROUPS`) serves only those groups plus `mow_tools`. No flag = all groups. A tool's group is its own `group` field when it has one, else the module's.
- As built (differs from or adds to the line above): the flag wins over the env, `--groups=a,b` works too, and `--groups all` or an empty value = every group; only `mow_tools` stays on, the other `knowledge` tools go off unless `knowledge` is named; a name no tool has is a stderr note (and a line in `mow_tools`), never a failure; a call to a tool whose group is off answers a result with `isError` and the `--groups` line that loads it (a name no module has stays JSON-RPC -32602); a tool's own `group` must be one lower-case word, else that tool is skipped and named; `--list` output gains `groups: { all, served, off, unknown, limited }`; `catalog.js` takes `--out <file>` and `--skills <dir>` and fails on skill line limits only with env `ARSENAL_SKILL_LIMITS=1` (commented line in `test/run.sh`).
- Groups of `arsenal`: `knowledge`, `mod` (info, new, check, fix, diff, gen, which file wins, upgrade, port plan, pack), `together` (clashes, patch mod, multiplayer sync), `units` (find, stats, change, equipment, look, entity), `weapons` (weapon find and change, balance, price), `text`, `maps` (maps, missions, modes, place), `bots`, `play` (status, log, crash, settings, modes, bots info), `coach` (match-up, armour, army, counter), `run` (the launch tools and the recorded routes), `assets` (models, textures, effects, sound), `scripts` (interaction and mission scripts), `robz` (the RobZ Realism mod). New groups may be added, same style.
- `tools/mcp/pack/pack.js` (lib + CLI): `list` (pieces, groups, sizes), `zip --piece <id> | --group <id> | --all --out <file>`, `install --piece|--group|--all --target claude-code-user | claude-code-project:<dir> | claude-desktop [--write]`, `uninstall ...`. Install previews unless `--write`; it copies skill folders into the target's skills folder and merges MCP server entries into the target's config (backup first, other entries untouched). Tests never touch the real user config: every target path can be overridden (`--home <dir>`).
- The GUI page (ext `claude`) shows every piece with its own download, the groups, the full download and Install into Claude, on every game tab.
