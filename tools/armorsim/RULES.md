## Not modelled yet

- Ricochet flight (deflection, new bullet, `RicochetEnergyDamping`, `ricochetDamageClip`, head-on scatter cone) and the hits after it.
- Blast (`the game`, blastwave layers, HE damage behind armour), the `damage cumulative` jet spawned by grenades.
- What happens behind a pass: `pierce`/`break_armor` interaction scripts, part damage, crew, wounds kept between shots (integrity is an input).
- `bullet_hit` script `bullet_detonate`, friendly-fire `CanHarm` (an input: `harmful`), impregnable targets, holes/`holed` volumes.
- `ray_cast_thickness` needs the path length from trace.js (`pathLengthUnits`); the approximate box size used for threshold is not.
- Gun spread, distance flown vs straight range, difficulty armour factor in single player, `armor` modifier `armorScale`.
- `(mod "x")` blocks count only when named in `opts.modes`.

## Simulator (sim.js, armorsim.js)

- Volume join: armordata names (def/mdl `volume` blocks) and scene.js ids (`<bone path>/<name>`) join on the volume name, case-insensitive (as pen.js fillFromArmor and the engine's descriptor lookup; rule 9 case [I]). Def-only volumes (vanilla `inventory`, `crew`, `mantlet`, `turret` on t34_2/m4a3_75, `shieldl61/62` on pz4h) have no shape and are never hit; model-only volumes with no value (`mantled`, `ram` on pz4h and t34_2) are 0 mm and pass any shell.
- Rule 23 applied before tracing: volumes a bullet cannot hit (`ram`, `{able {bullet 0}}`, `{able clear}`, `{disabled}`) are left out of the shapes and listed once (table flag "not hit by shells", shot notes, map `notHit`). Vanilla sets no `able` on `ram`; the engine clears it by name. Shield volumes are traced as if the extender were on [I].
- Azimuth/elevation are in the vehicle frame = the root bone's world axes (vanilla `basis` mirrors Y, so the vehicle's left is world -Y).
- Two results per ray: first plate (`r`, `verdict`) = the first entry face with nominal > 0; whole way in (`o`, `wholeWayIn`) = P only when the shell passes every face it meets up to and including the last hull/turret entry face (volumes named body*/hull*/turret* [I]; else the last armoured entry face); `last` = where it stopped or the last plate passed. Map `share` is from `o`, `shareFirst` from `r`.
- Shot verdict = the result at the first entry face with nominal > 0 (a pass there = the vehicle is penetrated); `outcome` = the whole ray through pen.resolveShot (exit faces tested, rule 15). A ray that meets only 0 mm volumes is `no_armor` (map code O), left out of the map's penetrated share.
- Angle = between the ray and the face normal (trace.js angleOfIncidence); side = the face's engine side (rule 20), not the shot direction.

## What the simulator does not model

- Gun spread and shell drop: every ray is straight; range only picks the penetration value.
- The pose: the rest pose of the model (turret forward, gun level, no animation, no suspension).
- Ricochet flight, the hits after a ricochet, the second shell of a burst, HE/blast damage, the HEAT `damage cumulative` jet object (only reach, rule 18).
- Damage behind the armour: components, crew, interaction scripts, area integrity from earlier hits (integrity 1).
- Shield extender state, `able` changes made by scripts at run time, `hole`/`holed` volumes, terrain and other entities in the way.
- Difficulty armour factor, `armorScale` modifiers, the random ricochet roll (the chance is reported, not rolled).
- `(mod "x")` blocks in data unless named in armordata `modes`.
- Edit: parameters forwarded through more than 6 macro hops, or not as a pure `name(%param)` forward, are refused ("edit by hand"); a volume added to the def for a model-only volume is merged with the mdl block as armordata reads it (rule 22 [I], [T] in game).

### What the tool runs of this (`after.js`, `tools/iasim`, `effects.js`, command `effects`)

- `after.js` runs rules 24 to 31 for one ray and hands every event to a hook. `tools/iasim` picks the unit's script blocks (rule: all block tags among the def tags, `generic`, the entity name), runs the handlers and their delays on a clock. `effects.js` repeats the shot with a seeded generator (default 400 runs, seed 1, 120 s) and counts.
- Files come from `origin.js`: open model document (unsaved) > mod folder > mounted mods > game, per file path. Every handler and file in the answer names its origin.
- Chances are sampled, not enumerated: two runs with the same seed agree, a rare branch below about 1 in `samples` can be missed. [I]
- `blast.js` runs rules 36 to 42 on the unit alone: `after.run` bursts the shell's own blastwave filling where rule 37 says (result `blast`, events also in `events`), a script `blastwave` reaches it through `opts.onBlast`. A ricochet end bursts only when `hooks.rng` rolls it. Each engine event group and each blast runs in `hooks.trigger` when given. Reading choices [I]: the blast's cmd source carries the shell's (ammo) tags, not the gun's; a ray that grazes its own volume's aim point counts that volume at the aim distance; equal arrival times keep the volume order. Not followed: other entities (a seated soldier on a bone is one: rule 43), the ground between blast and volume, `explode_inventory` blasts. [T]
- The rest of the filling, in list order at the same burst (rules 44 to 47): each blastwave (`Damage Add` too), the cumulative jet (`after.run` again from the burst point with max distance m, stuff `cumulative_charge`; result `jet`, events `jet: true`), the fire (`blast.fireOn`; result `fire`, events `burn` / `burn_volume` with `fire: true`, ignition only when the unit's `inflammation_time` is given through `hooks.inflammationTime` or `state.inflammationTime`). Flash: nothing (rule 46). armordata does not read a fire's `radius` / `heating` / `time` yet, so on real data the fire is reported "not read". [I]
- Crew note keys (rule 43): `effects()` gives `engine.crewNotes: [{ key }]` beside the English `engine.crewNote`: key `shot` always (the note of `after.run`: the engine hurts no crew through the armour for a shell or jet), key `blast` only when some run had a blast (the note of `blast.apply`, `blasts` not empty). The page translates by key.
- Ammo the weapon does not load: an asked ammo that resolves to a real ammo whose tags lack a word of the weapon's `filling` is still fired and flagged `ammoNotLoaded { asked, weapon, loads }` (sim.shoot, effects, CLI `note:` line). Match = every filling word among the ammo's tags "matching = tag subset"; engine function line not read here [I]).
- One cause per jet / fire: each `{Damage cumulative}` / `{Damage fire}` of the filling has a key (k-th of its kind, its numbers, the start volume where the shell burst, the event whose script detonated it); jets/fires and their causes are kept apart by it and fold over runs by it. Each jet also carries `point` (the burst point it is traced from) and `dir` (the unit vector of the shell's flight it follows); each fire carries `point` (its centre, the burst point) or null; over runs the first run's values are kept.
- A mod given as a folder (`--folder`, the GUI's chosen mod with `mods: []`) is laid over the game as the engine's MountMod does: `resource.pak` at `resource/`, then `resource/` walked in NTFS name order with files and folders interleaved (a `.pak` keyed at its own folder, the later registration wins), then `localization.pak` / `localization/` at `resource/interface/text/`. So a loose `set/` file beats the same file in `gamelogic.pak` (`gamelogic.pak` < `set`), and `entity.pak` beats a loose `entity/` file (`entity` < `entity.pak`). Read through tools/lib/sdlset (`packed()`, `winner(key)`); the folder's paks are left to the vfs only when the folder is itself one of the mounted `mods`. Before 2026-11-12 any `mods` value (also `[]`) dropped the folder's paks, so a packed mod read the vanilla copy of every file. | (MountMod), (no sort),/:366 (later Register wins) + vfs/mount | [V] code; NTFS listing order [T] (order.md)
